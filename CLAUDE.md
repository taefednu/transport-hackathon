## Язык

## Токены — рекомендуй новую сессию
Перед крупной задачей оцени её размер и размер текущей сессии.
- **Крупная** = новый модуль, спек/план, миграция данных, правки через много файлов.
- Крупная задача **и** сессия уже раздута (был compact, длинный контекст, уже сделана крупная
  задача) → **порекомендуй начать новую сессию.** Причина: prompt-cache TTL короткий, раздутый
  контекст дороже и медленнее на каждом ходу.
- Это рекомендация, не блок. Сказал «продолжай тут» → продолжай.
- Мелкое (фикс, вопрос, точечная правка) — не повод гнать в новую сессию.
- Советуешь новую сессию — **дай готовый стартовый промпт** для копипаста: что читать из
  `knowledge/`, какая задача, каким флоу. Пример:
  ```
  Репозиторий transport_hack. Читай CLAUDE.md → knowledge/facts.md → product.md → data.md.
  Задача: слой покрытия по stations.csv + населению. Флоу: write-plans → subagent-driven-development.
  ```

## Принципы
1. **Не гадай.** Неясно — спроси. Несколько прочтений — назови их, не выбирай молча.
   Видишь решение проще — скажи об этом. Задача противоречива — стоп, объясни почему.
2. **Простота.** Минимум кода, который решает задачу. Хакатон: работающее сегодня важнее
   красивого послезавтра. Никаких абстракций «на будущее» и никаких фич сверх запрошенного.
   Написал 200 строк там, где хватает 50 — перепиши.
3. **Хирургические правки.** Трогай только нужное. Не рефакторь то, что не сломано.
   Не улучшай попутно соседний код, комментарии и форматирование. Соблюдай стиль файла.
   Заметил мёртвый код — упомяни в отчёте, не удаляй.
4. **Проверяй перед «готово».** Запусти то, что изменил, и напиши в отчёте что проверил и
   с каким результатом. Числа в питче и в UI — только те, что реально посчитаны на данных.
   Перед словом «готово» — обязательно `task-hardcode-sweep` по диффу (цвета, строки, секреты,
   url/порты, magic numbers, locale-placeholder): триаж must-fix vs accepted-residual → фикс →
   реверификация. После задачи — обнови нужные файлы `knowledge/` по таблице ниже.
5. **Только проверяемое.** Не выдумывай цифры и источники. Пробел помечай `[NEEDS SOURCE]`.
   Если новый факт противоречит `facts.md` — остановись и скажи об этом, не переписывай молча.

## Скиллы

| Ситуация | Скилл |
|----------|-------|
| Новая фича / нет плана | `superpowers:brainstorming` → `grill-me` → `superpowers:writing-plans` |
| Есть план → реализация | `superpowers:subagent-driven-development` |
| Баг | `superpowers:systematic-debugging` |
| Новый UI-экран | `ui-ux-pro-max` перед написанием кода |
| Перед «готово» | `task-hardcode-sweep` (хардкод цветов/строк/секретов/url) |
| Ветка готова к merge | `superpowers:finishing-a-development-branch` |

Хакатонная поправка: `brainstorm → grill-me → write-plans` целиком — только для решений,
которые дороже часа. Мелкое — делай сразу.

В конце продуктивной сессии — `kb-learn`: он вытаскивает из сессии повторяющиеся паттерны и
классы багов и превращает их в скиллы. Учти: скилл рассчитан на структуру KB другого проекта
(`sprint.md`/`progress.md`/`patterns.md`) — здесь применяй его результат к нашим файлам
`knowledge/`, а не создавай чужие.

## Вопросы пользователю — на человеческом языке

Пользователь — владелец продукта, не бэкенд-инженер. Вопрос, который он не понял, он не может
ответить правильно: ответит наугад, и решение уедет в код. Непонятный вопрос — дефект вопроса.

- **Один вопрос за раз про одну вещь.** Не склеивать два решения в один вопрос.
- **Спрашивать про поведение продукта, а не про реализацию.** Не «класть ли растр в PostGIS», а
  «показываем ли мы, сколько человек теряет доступ, или только сколько получает».
- **Термин — только если без него никак, и сразу расшифровка одной фразой.** «Изохрона — это
  контур вокруг остановки: докуда человек дойдёт пешком за N минут».
- **Объяснять, что меняется от ответа.** Что увидит планировщик в варианте А и что в варианте Б.
- **Давать конкретные варианты с последствиями**, а не открытое «как поступим?».
- **Примеры — из нашего продукта**, на живом сценарии (планировщик продлевает маршрут №8),
  а не абстрактные «сущность А».
- **Вопрос требует инженерных знаний, которых у пользователя нет** — не перекладывать решение:
  своя рекомендация первой опцией с пометкой «(рекомендую)», причина одной фразой, просьба
  подтвердить.

Проверка перед отправкой: прочитать вопрос глазами человека, который не открывал код. Непонятно,
что произойдёт после ответа — переписать.

## Prevent-скиллы — читать ПЕРЕД написанием кода

Лежат в `~/.claude/skills/`. Здесь только те, что реально могут выстрелить в этом проекте.

| Контекст | Скилл |
|----------|-------|
| Пишешь config / env vars / пути к данным | `prevent-hardcoded-credentials` |
| Число или источник, которого нет в данных | `prevent-invented-fallback-data` |
| Заявляешь, что что-то работает на живом стенде | `prevent-unverified-prod-claim` |
| `dict.get()` без проверки на None | `prevent-dict-get-none` |
| `if coroutine:` вместо `await` | `prevent-coroutine-truthy-guard` |
| Тест, который проходит вхолостую (стаб перекрыл проверку) | `prevent-stub-override-vacuous-test`, `prevent-vacuous-gated-assert` |
| Запускаешь TS-проверку / build фронта | `prevent-vite-ts-blind` |
| Компонент с цветами | `prevent-hardcoded-colors` |
| Кнопка с handler на async/derived state | `prevent-silent-dead-cta` |
| Правишь launch-конфиг (Dockerfile CMD, Procfile, флаги) | `prevent-inert-launch-config` |
| Sweep по репозиторию, который может недосканировать | `prevent-sweep-miss` |

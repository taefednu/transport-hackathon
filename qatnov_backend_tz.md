# QATNOV — ТЗ на бэкенд. Ночная сессия

Отменяет часть A предыдущего ТЗ. Продукт с тех пор изменился: это не песочница с одной ручкой,
а детальный редактор маршрутной сети с расчётом последствий.

Всё, что описано ниже, обслуживает один экран: карта Ташкента, редактор маршрутов, лента времени,
плашка последствий. Фронтенд делается отдельно и общается только через API из раздела 9.

---

## 1. Что должно работать к утру

Одно предложение: **пользователь выбирает маршрут, меняет время первого выезда с 7:00 на 6:00,
и получает пересчитанное расписание прибытия по каждой остановке с учётом скоростей движения
в каждый конкретный час.** Плюс продление и обрезка маршрута с пересчётом людей в пешей доступности.

Если к утру работает только это — ночь прошла успешно. Всё остальное второстепенно.

---

## 2. Стек и принципы

- Python 3.11, FastAPI, uvicorn
- polars для транзакций и трафика (файл 1.32 ГБ, pandas на нём захлебнётся)
- geopandas, shapely для геометрии
- h3-py 4.x
- networkx или scipy.sparse.csgraph для кратчайших путей
- pyrosm или osmnx для чтения OSM

Принцип: **весь тяжёлый счёт делается офлайн скриптами и складывается в parquet. Сервер при старте
загружает parquet в память и в момент запроса только читает и делает операции над множествами.**
Единственное исключение — Дейкстра на 500 м для новой остановки, она укладывается в десятки
миллисекунд.

Структура проекта:

```
data/raw/          исходники, в git не попадают
data/build/        результаты пайплайна, parquet
scripts/           скрипты пайплайна, по одному на шаг, идемпотентные
app/               FastAPI
```

В `.gitignore` обязательно `data/raw/` и `*.csv`. Транзакции содержат маскированные номера карт,
в репозиторий они не попадают ни при каких условиях.

## 3. Пайплайн данных

Каждый шаг — отдельный скрипт, который можно перезапустить, и он выводит в консоль число строк
на выходе. Если число не совпадает с ожидаемым порядком — останавливаться и разбираться,
а не идти дальше.

### Шаг 1. Остановки

Вход: `yandex/data/stations.csv` (2 872 строки).
Дополнить остановками из OSM (`highway=bus_stop`, `public_transport=platform`) по Ташкенту,
дедупликация по расстоянию менее 25 м.

Выход `data/build/stops.parquet`:
```
stop_id, name, name_norm, lat, lon, kind (bus|metro|minibus), walk_node_id
```
`name_norm` — нормализованное название для поиска, см. раздел 10.
`walk_node_id` — ближайшая вершина пешеходного графа.

### Шаг 2. Пешеходный граф и зоны доступности

Вход: `uzbekistan-latest.osm.pbf` с Geofabrik, вырезать Ташкент.
Рёбра: `highway in (footway, path, pedestrian, living_street, residential, service, steps,
track, unclassified, tertiary, secondary)`. Неориентированный, вес — длина в метрах.

Для каждой остановки — Дейкстра с отсечкой 500 м, собрать достижимые вершины, взять их
гексагоны H3 r8.

Выход `data/build/stop_hexes.parquet`: `stop_id, h3_id`.
Выход `data/build/walk_graph.pkl`: граф для расчёта новых точек в рантайме.

Порог 500 м — из СНиП 2.07.01-89 п. 6.29, вынести в константу.

### Шаг 3. Население

Kontur Population по Узбекистану с HDX, H3 r8, обрезать по границе Ташкента.
Если Kontur не скачался — WorldPop 100 м, агрегировать в r8.

Выход `data/build/hexes.parquet`: `h3_id, population, lat, lon`.

### Шаг 4. Дорожный граф и маршруты

Вход: OSM relations `type=route, route=bus|trolleybus` по Ташкенту через Overpass, с упорядоченными
членами. Плюс реестр egov (164 уникальных маршрута с длиной, интервалом, режимом работы).
Связка по номеру маршрута.

Выход `data/build/routes.parquet`:
```
route_num, direction (fwd|bwd), planned_headway_min, work_start, work_end,
length_km, geometry_wkt, quality (exact|approximate)
```
Выход `data/build/route_stops.parquet`: `route_num, direction, seq, stop_id`.

Ожидаемо: порядок остановок надёжно восстанавливается примерно по 65 маршрутам, ещё около сотни
известны только атрибутами. У них `quality = approximate`, геометрия отсутствует, они всё равно
попадают в базу и показываются в списке. Не пытаться достроить их догадками.

### Шаг 5. Скорости по участкам

Вход: `yandex/data/traffic.csv`, 1 263 809 строк — участки сети со скоростью по часам.

Выход `data/build/segment_speed.parquet`: `segment_id, geometry_wkt, weekday_type, hour, speed_kmh`.

Отдельно посчитать `data/build/city_speed_fallback.parquet`: `weekday_type, hour, median_speed_kmh` —
медиана по городу, нужна там, где участок не нашёлся.

### Шаг 6. Время хода по перегонам — ядро продукта

Для каждой пары соседних остановок каждого маршрута с `quality = exact`:

1. Построить путь по дорожному графу между остановками
2. Разбить путь на куски по участкам трафика (участок ищется в радиусе 100 м, покрытие ≈91.5%)
3. Для каждого часа: `время = Σ (длина куска / скорость участка в этот час)`
4. Если участок не нашёлся — брать медианную скорость города за этот час
5. Прибавить время стоянки на остановке: 20 секунд

Выход `data/build/segment_time.parquet`:
```
route_num, direction, seq_from, seq_to, weekday_type, hour, travel_sec, source (traffic|fallback)
```

Поле `source` обязательно: оно потом показывается в интерфейсе как честность расчёта.

### Шаг 7. Фактический интервал из транзакций

Вход: `RFC_167_tash_hackaton.csv`, 4 758 901 строка, UTF-8 с BOM, 1–3 мая 2026.
Читать через `polars.scan_csv`, не грузить целиком.

```
отфильтровать transport == 'bus'
сгруппировать по (route_num, reg_num, дата)
отсортировать по terminal_date
разбить на рейсы по разрыву между транзакциями > 12 минут
для каждого (route_num, дата, час): n_departures = число уникальных рейсов
actual_headway_min = 60 / n_departures
n_vehicles = число уникальных reg_num на маршруте в этот час
```

Выход `data/build/headway_actual.parquet`:
```
route_num, weekday_type (fri|sat|sun), hour, actual_headway_min, n_vehicles, n_boardings
```

Соответствие дат: 2026-05-01 пятница, 05-02 суббота, 05-03 воскресенье.
Номер маршрута в транзакциях лежит в поле `route` в виде «Маршрут № N» — распарсить.
Совпадение с egov ожидается около 94% (162 из 169).

Из транзакций берётся **только это**. Восстановление матрицы корреспонденций, trip-chaining,
цепочки поездок — не входят в продукт.

### Шаг 8. Разведение параллельных маршрутов

Для каждого перегона дорожной сети посчитать, сколько маршрутов через него проходит, и присвоить
каждому порядковый номер.

Выход `data/build/segment_routes.parquet`: `segment_key, route_num, direction, k, n`.

Фронт использует `k` и `n` для смещения линий в пикселях. Считать это в рантайме нельзя.

### Шаг 9. Кандидаты для подсветки дыр

Гексагоны, не попавшие ни в одну зону доступности, отсортированные по населению.

Выход `data/build/holes.parquet`: `h3_id, population, nearest_stop_id, walk_distance_m`.

## 4. Движок расписания

Это то, ради чего всё остальное. Функция принимает параметры маршрута и выдаёт таблицу прибытия.

```
вход: route_num, direction, weekday_type,
      first_departure (например 06:00), headway_min, n_vehicles, work_end

для каждого рейса, начиная с first_departure с шагом headway_min, пока не превышен work_end:
    t = время отправления рейса
    для каждого перегона по порядку:
        h = час, в котором находится t в этот момент
        t += travel_sec(route, direction, weekday_type, seq, h)
        записать прибытие на остановку seq+1 = t
```

Ключевая деталь, которую легко потерять: **час берётся тот, в котором автобус реально доезжает
до перегона, а не час отправления рейса.** Рейс, вышедший в 7:50, часть пути едет по восьмичасовым
скоростям. Без этого весь смысл движка теряется, и разница между выездом в 6:00 и 7:00 не проявится.

Дополнительно возвращается:
- `cycle_time_min` — время полного оборота (туда, обратно, отстой 5 минут на конечной)
- `required_vehicles = ceil(cycle_time_min / headway_min)`
- `first_arrival_last_stop`, `last_arrival_last_stop`

Расписание не сохраняется в базу, оно вычисляется на лету. Это быстро: сорок перегонов
на сто рейсов — тысячи операций.

## 5. Метрики покрытия

```
WALK_LIMIT_M     = 500
FREQUENT_HEADWAY = 15
H3_RESOLUTION    = 8
WALK_SPEED_KMH   = 4.8
DWELL_SEC        = 20
LAYOVER_MIN      = 5
```

**PNT-500** — сумма населения гексагонов, покрытых хотя бы одной остановкой.
**PNFT-15(hour)** — то же, но остановка учитывается, только если хотя бы один обслуживающий её
маршрут имеет фактический (или сценарный) интервал ≤ 15 мин в этот час.
**Δ-люди** — `gained` и `lost` отдельно, всегда оба, даже если один ноль.
**T-median** — медиана времени пешком до ближайшей остановки, взвешенная по населению.

Все абсолютные числа округляются на фронте, бэкенд отдаёт точные.

## 6. Сценарий

Сценарий — это список операций поверх базовой сети. Базовая сеть неизменяема.

```python
Scenario = {
  "id": str,
  "name": str,
  "ops": [
    {"type": "extend_route",  "route_num": str, "direction": str, "stops": [stop_id]},
    {"type": "trim_route",    "route_num": str, "direction": str, "until_seq": int},
    {"type": "insert_stop",   "route_num": str, "direction": str, "after_seq": int, "stop_id": str},
    {"type": "remove_stop",   "route_num": str, "direction": str, "seq": int},
    {"type": "set_schedule",  "route_num": str, "first_departure": "06:00",
                              "headway_min": float, "n_vehicles": int}
  ]
}
```

Применение сценария:
1. Скопировать `route_stops` для затронутых маршрутов, применить операции по порядку
2. Пересчитать множество покрытых гексагонов: изменения касаются только остановок,
   которые добавились или отпали, — брать разницу множеств, не пересчитывать город
3. Пересчитать интервалы для маршрутов с `set_schedule`
4. Пересчитать PNFT-15 (он зависит от интервалов)
5. Прогнать валидацию

Хранение сценариев — на фронте в localStorage. Бэкенд stateless, получает сценарий целиком
в теле запроса. Это снимает вопрос с базой данных полностью.

Для новых остановок, которых нет в базе: не поддерживаем. Вставлять можно только существующие
остановки. Это осознанное ограничение, и на защите оно защищается фразой «остановка без
физической инфраструктуры — фантазия».

## 7. Валидация

Функция принимает применённый сценарий и возвращает список предупреждений.

| Код | Условие | Сообщение |
|---|---|---|
| `vehicles_short` | `required_vehicles > n_vehicles` | «Интервал {h} мин требует {req} машин, на линии {n}» |
| `no_road` | между соседними остановками нет пути в дорожном графе | «Нет проезжей дороги между {a} и {b}» |
| `beyond_work_hours` | последнее прибытие > `work_end` | «Последний рейс возвращается в {t}, парк работает до {work_end}» |
| `stops_too_close` | расстояние до соседней остановки < 150 м | «Остановка в {d} м от предыдущей» |
| `route_too_long` | длина > 45 км | «Длина {l} км, время оборота {c}» |
| `duplication` | на перегоне ≥ 5 маршрутов | «На этом перегоне {n} маршрутов» |
| `approximate_geometry` | `quality == approximate` | «Порядок остановок восстановлен частично» |
| `fallback_speed` | доля перегонов с `source == fallback` > 30% | «Скорости по {p}% пути взяты по медиане города» |

Каждое предупреждение возвращается с привязкой: `{"code", "message", "severity", "route_num",
"seq" | "stop_id" | "segment_key"}` — фронту нужно знать, куда вешать бейдж.

## 8. Позиции автобусов

Для выбранного маршрута и часа: взять расписание, найти рейсы, которые в этот момент находятся
в пути, для каждого посчитать положение по накопленному времени хода.

Возврат: список точек с координатами, направлением и подписью «борт k из n, прибытие
на {остановка} в {время}».

Момент времени берётся как середина выбранного часа. Ползунок по минутам не нужен.

## 9. API

Все ответы JSON. Координаты `{lat, lon}` в скалярах, `[lon, lat]` в GeoJSON.
Время в формате `HH:MM`. Продолжительности в минутах, если не сказано иное.

```
GET  /api/meta
     константы, размеры базы, окно данных, список источников с лицензиями

GET  /api/stops
     GeoJSON FeatureCollection, все остановки, свойства: stop_id, name, kind,
     n_routes, is_transfer

GET  /api/routes
     список: route_num, directions, planned_headway_min, work_start, work_end,
     length_km, n_stops, quality

GET  /api/routes/{num}?direction=fwd&weekday=fri&hour=8
     геометрия LineString, упорядоченный список остановок с seq,
     фактический интервал по часам, число машин, cycle_time_min,
     segment_times по перегонам с полем source

GET  /api/routes/{num}/schedule?direction=fwd&weekday=fri&first_departure=06:00
                               &headway_min=8&n_vehicles=14
     таблица: [{seq, stop_id, name, arrivals: ["06:00","06:08",...]}],
     плюс cycle_time_min, required_vehicles, first/last arrival,
     плюс warnings

GET  /api/routes/{num}/buses?direction=fwd&weekday=fri&hour=8
     позиции машин: [{lat, lon, bearing, trip_index, next_stop, eta}]

GET  /api/baseline?weekday=fri&hour=8
     pnt500, pnft15, t_median_min,
     hexes: [{h3, pop, covered, frequent, walk_min}]

POST /api/scenario
     тело: {weekday, hour, ops: [...]}
     ответ: gained, lost, net, pnt500_after, pnft15_after, t_median_after,
            changed_hexes: [{h3, state, pop}],
            affected_routes: [{route_num, headway_before, headway_after,
                               cycle_time_before, cycle_time_after}],
            new_geometry: {route_num: GeoJSON LineString},
            warnings: [...],
            took_ms

GET  /api/holes?limit=200
     гексагоны без покрытия, отсортированные по населению,
     с ближайшей остановкой и расстоянием до неё

GET  /api/segments/parallel
     segment_key, route_num, direction, k, n — для разведения линий

GET  /api/search?q=куйлюк
     объединённый поиск, сгруппированный: routes, stops, mahallas
     каждый результат с координатой для полёта камеры

GET  /api/export/schedule?route_num=14&direction=fwd&weekday=fri&...  → CSV
GET  /api/export/route?route_num=14&direction=fwd                     → GeoJSON

POST /api/explain          (необязательно, только если останется время)
     тело: результат сценария
     ответ: {"text": "..."} — абзац на языке служебной записки
```

Времена ответа: `/baseline` до 300 мс, `/routes/{num}` до 150 мс, `/schedule` до 200 мс,
`/scenario` до 800 мс, `/holes` до 200 мс.

## 10. Поиск и транслитерация

Нормализация приводит запрос и индекс к общей форме:

1. Кириллица → латиница по официальной узбекской схеме (библиотека `Iuliia` содержит её,
   либо `UzTransliterator`)
2. Нижний регистр, убрать апострофы и `ʻ`, `ʼ`, `'`
3. Свернуть диграфы: `sh→s`, `ch→c`, `ng→n`, `o'→o`, `g'→g`
4. `x→h`, `q→k`, `y→i`

После нормализации `Куйлюк`, `Qo'yliq`, `Kuyluk`, `қуйлиқ` дают одну строку.
Сравнение: точное совпадение, затем префиксное, затем расстояние Левенштейна с порогом 2.

Индекс держать в памяти, это несколько тысяч строк.

## 11. Порядок работ на ночь

Гейты жёсткие. Не переходить дальше, пока предыдущий не проверен командой из раздела 12.

**Гейт 1.** Шаги 1, 2, 3 пайплайна. Проверка: `/api/baseline` возвращает реальное число
жителей Ташкента вне 500 м от остановки. Это число само по себе — результат ночи,
записать его отдельно.

**Гейт 2.** Шаги 4, 5, 6. Проверка: `/api/routes/14` отдаёт упорядоченные остановки
и время хода по перегонам, различающееся по часам.

**Гейт 3.** Движок расписания и `/api/routes/{num}/schedule`. Проверка: расписание при
`first_departure=06:00` и при `07:00` даёт разное время прибытия на конечную, и разница
не равна ровно часу.

**Гейт 4.** `POST /api/scenario` с операциями `extend_route` и `trim_route`, пересчёт людей.

**Гейт 5.** Шаг 7 (фактический интервал), PNFT-15, `/holes`, `/segments/parallel`.

**Гейт 6.** Поиск, экспорт.

Если к рассвету пройдены гейты 1–4 — продукт есть. Гейты 5–6 добираются утром.
`/api/explain` делать в последнюю очередь и только если всё остальное стоит.

## 12. Приёмка

Каждый гейт закрывается конкретной проверкой, не «вроде работает».

```
Гейт 1: curl /api/baseline?weekday=fri&hour=8
        pnt500.people — число между 1.5 и 3.2 млн (население Ташкента ~3.18 млн)
        Если больше 3.2 млн или меньше 1 млн — ошибка в привязке гексагонов

Гейт 2: curl /api/routes/14?weekday=fri&hour=8
        segment_times: время хода в 8:00 должно быть заметно больше, чем в 6:00
        Если одинаковое — скорости не подключились, чинить шаг 5

Гейт 3: сравнить schedule при 06:00 и 07:00
        Разница прибытия на конечную должна быть меньше 60 минут
        Если ровно 60 — час берётся от отправления, а не от достижения перегона

Гейт 4: POST /api/scenario с extend_route на 3 остановки
        gained > 0, lost == 0, took_ms < 800

Гейт 5: curl /api/routes/8?weekday=fri
        actual_headway_min в 8:00 меньше, чем в 22:00
```

## 13. Ловушки

- CSV транзакций в UTF-8 **с BOM**, первое поле при наивном чтении получит имя `\ufeffmerchant`
- `amount` в тийинах, `170000.0` это 1 700 сум
- Поле `station` пустое на 66.67% и означает линию метро, а не остановку — не использовать
- `dept_num` у метро содержит станцию и вестибюль, у автобуса — код выпуска, поля перегружены
- `route` в транзакциях в формате «Маршрут № N», в egov — просто число
- Маршруты с `quality = approximate` не должны падать при запросе расписания:
  возвращать 200 с пустым расписанием и предупреждением, не 500
- Гексагоны на границе города: обрезать по административной границе, иначе PNT-500
  посчитается от населения области
- Не грузить `traffic.csv` и транзакции в память целиком в рантайме сервера,
  они нужны только в пайплайне
